# Отчёт: VK Видео и RUTUBE для BMW MGU

**Архив аудита 0.4.0. Актуальный выпуск 0.4.1, телевизионный QR-вход VK и установка
через магазин описаны в [новом отчёте](RELEASE-0.4.1-RU.md).** Ограничения ниже
относятся к первоначальному preview и не заменяют текущую инструкцию.

Дата проверки: 7 ноября 2026 года. Репозиторий — `istt1899/x3`, ветка
`feature/mgu-vk-rutube`, тестовый релиз `media-preview-0.4.0`. Стабильные каталоги
магазина и RideTube 0.3.13 не заменены этой интеграцией.

## Итог и границы готовности

Собраны два отдельных приложения: `marku_vk_video` 0.1.0 и `marku_rutube` 0.1.0.
Они работают с одним расширенным `jap-ridetube-d` 0.4.0. Прежний интерфейс YouTube
0.3.13 включён в тестовый каталог с прежним архивом. Существующий компонент
«Кодировки • X3» сохранён в каталоге без изменений.

Это **кандидат для проверки**, а не обещание «после обычного обновления всё уже
заработает в машине». На PC проверены реальные сервисы, преобразование медиаданных,
контракты процессов, пакеты и симуляция интерфейса. На MGU новое приложение не
устанавливалось, аппаратный декодер и BMW MediaPlayer с новыми провайдерами не
проверялись.

| Возможность | Что действительно подтверждено | Что осталось |
| --- | --- | --- |
| YouTube | Старое приложение/прокси сохранены; сетевые тайм-ауты и изоляция адаптера проверены | Повторить регрессию на MGU после смены службы |
| VK поиск/публичное видео | Живые карточки, JPEG, подписанный MP4; короткий ролик подготовлен в H.264/AAC/MGYI на PC | Проверить картинку и звук на MGU |
| VK аккаунт | PKCE/state, собственный relay и обмен проверены тестами; ложного входа нет | APP_ID, зарегистрированный redirect, сервер HTTPS, разрешения Video API, реальный вход |
| VK личный контент | Не реализован; гостевой поиск не выдаётся за личную ленту | Подключить после подтверждения реальных прав приложения |
| RUTUBE | Живые главная/поиск/метаданные/HLS, миниатюры, настоящий device-code и pending | Подтверждение владельцем, реальный refresh/личные ленты и MGU |
| Linux FFmpeg | Собственный статический x86-64 ELF, хэш, ABI и лицензии проверены | Исполнение именно этого ELF на Linux/MGU |

## ТЗ и решение совета

Начальное [ТЗ](SPEC-RU.md) было сформулировано до реализации. Совет из трёх агентов
отдельно исследовал MGU/медиадвижок, VK и RUTUBE. После реализации проведён повторный
независимый аудит и исправлены найденные дефекты.

Три копии видеослужбы запускать нельзя: у существующего решения фиксированные
аудиоисточник SOME/IP 1046 → 1024 и поверхность `/dev/shm/mgu-video-ridetube`.
Поэтому используется один проигрыватель с тремя сокетами:

- YouTube: `/run/jap-ridetube-d/ctl.sock`;
- VK: `/run/jap-ridetube-d/vk.sock`;
- RUTUBE: `/run/jap-ridetube-d/rutube.sock`.

Владелец воспроизведения определяется сессией и поколением. Обычный поиск, показ
миниатюр и вход другого сервиса не меняют владельца. Stop, закрытие и новый Play
отменяют устаревшие продолжения. Перед новым декодером ожидается фактический выход
предыдущего, включая смену качества и ошибку старого ролика.

## Сеть и авторизация

Системный VPN на MGU не устанавливается. YouTube сохраняет текущий прокси из
`state/proxy.json`; VK/RUTUBE используют direct и не наследуют proxy.json или
HTTP_PROXY. Учётные записи и кэши разделены. Root хранит приватные JSON 0600;
сетевые/медиа-процессы работают с выделенным интернет-UID. Секреты передаются через
stdin и не попадают в интерфейс, argv, каталог или публичные отчёты.

У RUTUBE исследован [актуальный первый TV-клиент](https://rutube.ru/tv-release/webos.server/webos/).
Реально получен device code; неподтверждённый код правильно остаётся pending.
Это не доказывает завершённый вход, получение личных данных или refresh владельца.

VK использует гостевой web-поиск и извлечение публичных видео. Для входа подготовлен
[HTTPS relay](auth-relay/README.md): короткий QR ведёт к официальному VK ID,
а обмен кода на токен выполняет MGU с локальным PKCE verifier. Успех требует
проверки профиля и прав на видео. [SDK VK ID](https://github.com/VKCOM/vkid-web-sdk)
описывает вход; [схема Video API](https://github.com/VKCOM/vk-api-schema/blob/master/video/methods.json)
требует пользовательский токен. Доступ Video API для произвольного нового APP_ID
не гарантирован. Без этих внешних настроек полноценный аккаунт VK не включён.

## Медиа и поставка

Подписанные VK URL привязаны к User-Agent: сохраняется исходный заголовок выбранного
формата. Актуальный доверенный CA-набор включает HARICA; проверка HTTPS не отключена.
RUTUBE HLS загружается напрямую с закрытым рабочим каталогом фрагментов. FFmpeg
получает медиа через stdin, не имеет сетевых протоколов и без перекодирования
создаёт H.264/AAC-потоки для существующего плеера.

FFmpeg 9.0.2 собран из [официальных исходников](https://ffmpeg.org/releases/ffmpeg-9.0.2.tar.xz)
для baseline x86-64 Linux/musl: нет GLIBC-зависимостей, динамического загрузчика,
исполняемого стека или GPL/nonfree-компонентов. Поставка сопровождается точным
source bundle и лицензиями. Источники размещаются также по постоянному адресу
`catalog/ffmpeg-9.0.2-mgu-media-sources.tar.xz`; стабильный catalog.json при этом
не меняется.

Два приложения собраны как source-only, без BMW SDK и тестового SDK stub.
Нужен `mgu-deploy` ≥0.7.11 с восстановлением SDK из штатного donor на устройстве.
Автономная проверка установки должна запустить поставленный Linux FFmpeg на
синтетических MP4/TS; ошибку нельзя обходить. Программа не меняет кодировки машины.

## Исправления по повторному аудиту

1. Временная сетевая ошибка VK больше не стирает refresh token, включая только что
   ротированный. До проверки профиля состояние не считается успешным.
2. Изменение авторизации во время поиска/resolve публикуется в UI, сохраняется и
   планирует опрос только для актуального поколения; ошибка контента его не скрывает.
3. Любой остановленный видеодекодер учитывается до exit/close; смена сервиса не
   запускает второго писателя в общую видеоповерхность.
4. Смена качества VK/RUTUBE обновляет временную ссылку до удаления старого кэша.
   Ошибка resolve сохраняет прежнее воспроизведение; Stop не ждёт сеть.
5. Миниатюры RUTUBE уменьшаются штатным `?size=l` только на проверенном CDN без
   исходных query/fragment. Лимиты JPEG 4 MP/64 MiB сохранены.
6. Фатальная ошибка службы завершает её с кодом 1 для systemd Restart=on-failure;
   штатный Stop остаётся кодом 0.
7. Исправлены CA wiring yt-dlp, fileno для stdout, приватный HLS scratch, stdout
   ошибок и выбор совместимого минимального качества.

## Проверки

Финальный набор: 37 provider-тестов (21 VK, 16 RUTUBE), 7 worker, 6 mediafetch,
7 relay и 3 provider→relay. Проверки gateway, bridge, entrypoint и UI выполнены
на настоящем Node 8.17.0; relay — на Node 24.22.2. Пакеты приложений при двух
последовательных сборках совпали побайтно. Проверка release сверяет каждый
служебный файл с manifest и текущим исходником, зависимости, runtime, лицензии,
две независимые UUID, ограничения видео и отсутствие SDK.

Живые запросы подтверждают VK поиск/миниатюры/короткий MP4 и RUTUBE поиск/главную/
миниатюры/HLS. Из последнего реально прочитано 65536 байт MPEG-TS с корректной
синхронизацией даже при намеренно нерабочих proxy env. Это не проверка всего
длинного ролика. Нормализация MP4/TS проверена Windows FFmpeg; она подтверждает
код конвейера, но не выполнение поставленного Linux ELF.

Старые PC harness для network/deadline требуют современный Node и прошли на
Node 24. Полный Linux/SOMEIP/GPU набор на этой Windows-машине не подтверждён.
Хэши пакетов и явные признаки непроверенного MGU записаны в
[RELEASE-EVIDENCE.json](RELEASE-EVIDENCE.json).

## Как повторить

Из корня клона в PowerShell; пути Node 8, FFmpeg и проверенного исходного пакета
нужно заменить на свои. `media/runtime/FFMPEG.md` описывает сборку runtime.

```powershell
python -m unittest discover -s media/providers/tests -p 'test_*.py' -v
python -m unittest discover -s media/service -p test_worker.py -v
$env:MGU_TEST_FFMPEG='C:\tools\ffmpeg.exe'
python -m unittest discover -s media/service -p test_mediafetch.py -v
$env:MGU_TEST_NODE='C:\tools\node24\node.exe'
python -m unittest discover -s media/auth-relay/test -p test_provider_relay.py -v
& $env:MGU_TEST_NODE --test media/auth-relay/test/relay.test.js
$node8='C:\tools\node8\node.exe'
& $node8 media/service/test_gateway.js
& $node8 media/service/test_python_provider.js
& $node8 media/service/test_main.js
python media/tools/build_apps.py
& $node8 media/ui/test_model.js
python media/tools/build_release.py --base-service C:\artifacts\jap-ridetube-d@0.3.13.tgz --ffmpeg media/runtime/ffmpeg --source-bundle C:\artifacts\ffmpeg-9.0.2-mgu-media-sources.tar.xz
python media/tools/test_release.py
```

Опциональный настоящий сетевой smoke — `media/service/test_live_gateway.js --live`;
он использует настоящие guest API и неподтверждённый RUTUBE код, без BMW плеера.
Требуемые пути Python/pyz/Node22 задаются через переменные, описанные в этом файле.

## Перед стабильным обновлением

Сначала выполняются условия [приёмки](INSTALL-RU.md). Установленная общая служба
принадлежит исходному источнику RideTube: [Store привязывает обновления к origin](https://github.com/robertnisipeanu/mgu-store/blob/main/native/mgu-updater/js/updater.js).
Поэтому при продвижении общий сервис нужно опубликовать также в `istt1899/ridetube`,
затем объединить стабильный каталог x3 и проверить оба канала. Тестовая публикация
в x3 сама по себе не означает, что обычный Check now уже обновит автомобиль.
